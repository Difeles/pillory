## 1. Как понят продукт

Pillory — офлайн-first мобильное приложение (Flutter, iOS + Android) для домашней аптечки: лекарства, несколько упаковок с разными сроками годности, остатки с историей, категории, список покупок, необязательный трекер приёма. Поверх — «эмоциональный» слой: пастельная дизайн-система, анимации, haptics и две графические фишки: 3D-просмотр таблетки с кастомизацией и декоративная физическая сцена.

### Жёсткое разделение (ТЗ §3)

| | `Medicine3DModel` | `MascotCharacter` |
|---|---|---|
| Что это | Реалистичный объект: таблетка, капсула | Иллюстрированный персонаж UI |
| Лицо, глаза, рот, мимика | **Запрещены категорически**, в т. ч. в онбординге | Допустимы |
| Где | 3D-просмотр, кастомизация, физическая сцена, превью в карточке | Онбординг, пустые состояния, подтверждения, коллекция |

Два разных компонента и две разные модели данных; правило фиксируется тестами и документацией. Кастомная модель — только виртуальное представление, не идентификация препарата.

### Обязательные ограничения
- Без диагнозов, назначений, дозировок, оценки совместимости; нейтральная подсказка для просроченных.
- Данные локально (SQLite/Drift, миграции), без обязательной регистрации, без утечки названий лекарств в аналитику/AI/уведомления, возможность удалить данные.
- Остаток не уходит в минус; повторная отметка приёма не списывает дважды; упаковки с разными сроками не склеиваются.
- Доступность: крупный шрифт, screen reader, reduce motion, отключение haptics, альтернативы жестам, работа без 3D.
- 3D-движок не грузится на всех экранах; физика не работает в фоне; число объектов ограничено; 2D/2.5D не выдаётся за 3D; непроверенное не называется проверенным.

## 2. Риски, неизвестные, противоречия

### Блокеры
- **iOS и Android не настроены** (нет Xcode, симуляторов, CocoaPods, Android SDK, JDK). Все проверки этих платформ **заблокированы до установки инструментов**. Результаты на macOS desktop/web — промежуточные и не засчитываются как iOS/Android.
- **Тестовые устройства не определены.** Пока их нет, окончательные пороги производительности не утверждаются.
- Референсные изображения (§7 ТЗ) отсутствуют. Это **не блокирует** техническую разведку (она не про визуальный стиль интерфейса), но блокирует финальную оценку «попадания в стиль».

### Технические риски
1. **flutter_scene pre-1.0**: «minor releases can carry breaking changes» (за последние релизы 0.23 и 0.24 ломающие изменения были, см. §4.1). Нужны точные версии и `pubspec.lock`.
2. **flutter_scene_rapier — экспериментальный**: «The API may change between releases». Это кандидат, не основа.
3. **Флаг Flutter GPU** в `Info.plist`/манифесте vs «не грузить 3D на всех экранах» — [Тест].
4. **Ручное управление ресурсами**: forge2d требует явного `destroy`; в flutter_scene есть `Scene.dispose`. Утечки при повторных открытиях — [Тест].
5. **Поддерживаемые Android ABI/minSdk** для flutter_scene в changelog не указаны; для Rapier prebuilt-бинарники заявлены для arm64/armv7/x64 [Факт], но minSdk не указан — [Тест/чтение документации].
6. **Производительность на среднем Android** — неизвестна до появления тестовых устройств.
7. **Число тяжёлых зависимостей** (flutter_scene, Rapier, возможно Flame+forge2d) — решение по итогам спайка.

### Неизвестные решения (за вами)
- Минимальные версии iOS/Android и тестовые устройства.
- Допустим ли 2.5D как итог, если Rapier не пройдёт.
- Пороги домена: «скоро истекает», «заканчивается», единицы учёта (нужны до схемы БД, Этап 1).
- Шрифт с кириллицей; язык интерфейса.
- Источник 3D-ассетов (см. §5): кто и чем делает GLB.

### Противоречия и пробелы ТЗ
- §6/§27 требуют на Этапе 0 создать проекты и прототипы; текущие инструкции запрещают. Прототипы делаются только после вашего старта.

- §15.1 vs глобальный флаг Flutter GPU — см. риск 3.

## 4. Варианты реализации

### 4.1. 3D-рендер таблетки

**flutter_scene** — главный кандидат. [Факт: pub.dev]
- Версия 0.24.3 (опубликована ~8 дней назад на момент чтения), требует Flutter 3.47+ stable. iOS и Android — Supported (также Web через WebGL2, macOS, Windows, Linux).
- PBR-материалы, image-based lighting, источники света с тенями, glTF-импорт, `.fscene`, KTX2, анимации, пост-обработка.
- Включение Flutter GPU: `FLTEnableFlutterGPU` в `Info.plist`; `io.flutter.embedding.android.EnableFlutterGPU` в манифесте; при разработке `flutter run --enable-flutter-gpu`.
- Pre-1.0.

Из changelog, важное для Pillory [Факт]:
- **0.23.0: front faces теперь CCW. Вручную написанные индексные буферы и собственные `Geometry` должны поменять порядок обхода треугольников.** Это прямо касается процедурной таблетки: ошибка порядка обхода даст «вывернутую» геометрию.
- 0.24.0: `Geometry.uploadVertexData` принимает `TypedData`; `Scene.initializeStaticResources()` бросает исключение при ошибке; изменены интерфейсы `Geometry`, `Material`, `Camera`.
- 0.24.1: исправление шейдеров на Apple-платформах «вместо падения на Flutter 3.47».
- 0.24.2: `Scene.dispose` сразу освобождает render targets; после dispose рендер бросает `StateError`.
- Материалы: у импортированных материалов сохраняются имена (`Material.name`, 0.20.0); `MaterialParameters` с типизированными геттерами, `MaterialGroup` для массовой установки параметра, `KHR_materials_variants` (`MaterialsVariantsComponent`, `SceneModel.variant`).
- Камера: `OrbitCameraController` (0.22.1) — потенциально закрывает вращение/зум, нужна проверка жестов и инерции [Тест].
- Хуки на именованные узлы в glTF существуют (например суффикс `-split<N>` для разбиения), что косвенно подтверждает работу с именованными узлами, но **прямого описания сценария «найти узел `cap_top` и поменять ему цвет» я не видел** — [Тест].

Альтернативы (запасные, не рекомендуются): `model_viewer_plus` (WebView + `<model-viewer>`, minSdk 24) и `flutter_3d_controller` (обёртка над ним, последний найденный релиз окт 2024). WebView затрудняет интеграцию с физикой и контроль ресурсов — [Предположение]. Предрендеренные кадры не дают материалов в реальном времени.

Статья Flutter про Flutter GPU (2024) говорит «только main channel»; она устарела относительно страницы flutter_scene (stable 3.47). Работоспособность на stable 3.47.7 подтверждается только запуском — [Тест].

### 4.2. Интерактивная физика

**Кандидат A — flutter_scene + flutter_scene_rapier (полноценная 3D-физика).** [Факт: pub.dev]
- Версия 0.5.2, опубликована ~11 дней назад, издатель bdero.dev (тот же автор, что и flutter_scene), MIT. «Rapier 3D physics backend for flutter_scene», связка по FFI.
- **Помечен экспериментальным: «The API may change between releases».**
- Android (arm64, armv7, x64) и iOS (arm64 устройство и симулятор) — **готовые бинарники**, Rust не нужен; build hook скачивает библиотеку и проверяет контрольную сумму. Intel-симулятор iOS и Intel macOS собираются из исходников (нужен Rust).
- Возможности: rigid bodies, colliders, joints, scene queries (raycast, overlap, shapeCast), события столкновений и триггеры, kinematic character controller. Интеграция: `PhysicsWorld` в корне сцены, `RigidBody`/`Collider` на узлах, фиксированный шаг с интерполяцией.
- На странице **не упомянуты** капсульные/цилиндрические формы и drag — наличие и удобство — [Тест] (для таблеток нужны капсулы/цилиндры или составные коллайдеры; drag можно реализовать через raycast + impulse/kinematic-тело, но это не подтверждено).
- Сборка скачивает бинарник при build → нужен доступ к сети при сборке; офлайн/CI-политика — [Тест].
- Решение: **кандидат на полноценную 3D-физику, не выбор.**

**Резерв B — Flame + Forge2D (2.5D).**
- forge2d 0.15.2 (Box2D v3, `dart:ffi`, native assets): Android/iOS/web/desktop; для Android нужен NDK, для iOS — Xcode; «Nothing is garbage collected: destroy things explicitly»; Dart 3.12+. [Факт]
- flame_forge2d перешёл на Box2D v3 в 0.20.0 (по результатам поиска; точную версию проверить на pub.dev при старте) — ломающая миграция.
- Это **2.5D**: плоская физика + объёмное оформление. В документации и коде маркируется как 2.5D, не как 3D.
- Flame — не 3D-движок (ТЗ §5).
- Решение: **резерв, на случай если Rapier не пройдёт критерии.**

Окончательная технология **не выбирается** до практической проверки.

## 5. Стратегия геометрии

Порядок (решение принято, окончательный выбор вариантов — по итогам проверки):

1. **Первая проверка — простая процедурная таблетка в коде** (цилиндр со скруглёнными краями, овал, капсула из двух половин). Цель — быстро проверить рендер, освещение, жесты, смену параметров, а также порядок обхода треугольников (CCW с 0.23.0). Качество на этой стадии не является целью.
2. **Целевой вариант для качественных моделей — GLB** с отдельно именованными частями и материалами (например `body`, `cap_a`, `cap_b`, `score_line`; материалы `mat_body`, `mat_cap_a`, `mat_cap_b`). Имена нужны, чтобы менять цвет/roughness по частям, а не по всей модели.
3. **Окончательный выбор между процедурной геометрией и GLB** — после проверки:
   - качества (фаски, риска, силуэт, нормали, тени);
   - возможности менять материалы и цвета по частям в реальном времени;
   - сложности поддержки (кто делает и обновляет модели, пайплайн экспорта, размер файлов, обратная совместимость при обновлениях flutter_scene).

Открытый вопрос: кто создаёт GLB-ассеты (вы, дизайнер или генерация кодом в Blender) — решение за вами.

## 6. Критерии производительности

Прежняя гипотеза «≥55 FPS» **отменена как окончательный порог**. Теперь:

- **Ориентир для устройств с экраном 60 Гц: стабильные 60 FPS.**
- Измерения — **только в profile mode** на реальных устройствах; debug-режим и эмуляторы не засчитываются.
- Фиксируем не только средний FPS, а **длительность кадров** (UI и raster thread, процентили, самые долгие кадры) и **количество рывков** (кадры дольше ~16.7 мс) за сессию вроде 60 секунд активного использования. Инструмент — Flutter DevTools (Performance), тайминги кадров.
- Для устройств с 90/120 Гц ориентир отдельно (пока не определяем).
- **Окончательный числовой порог (допустимая доля медленных кадров, допустимая худшая длительность) не утверждается**, пока не определены тестовые устройства. До этого эксперименты собирают данные, а не выносят вердикт «прошёл/не прошёл» по производительности.
- Дополнительно фиксируем: память после повторных открытий экрана, время до первого кадра 3D-экрана, размер релизной сборки.
